**Status: `IN PROGRESS`** — eleven references pulled and read, 2026-09-18. Both
screens are built; the policy renders, and deletion is built against a stub
because the endpoint does not exist. His instruction, 18 Sept: *"do not forget
policy page and delete user part, and delete user deletes everything, and we
should have small button for this."*

---

## 0 · A CORRECTION TO THIS FILE'S OWN §3 — it named the wrong AI provider

§3 of the earlier draft said *"**Answers are generated by DeepSeek**, so a
question and the retrieved passages leave his server for that provider."*

**They leave for Google.** `app/services/ai/config.rb:236-237`:

```ruby
return 'gemini'   if env_api_key(Ai::Models::Gemini).present?
return 'deepseek' if env_api_key(Ai::Models::Deepseek).present?
```

Gemini is tested **first**, `.env.production` sets both keys and does not set
`AI_CHAT_PROVIDER`, so **Gemini wins** and the traffic goes to
`generativelanguage.googleapis.com`. `docs/PRIVACY.draft.md` already carries the
corrected sentence — the multi_magic session caught it there — but this spec was
never updated, and **`BRIEF.md` §1 still has "Provider | DeepSeek" in its
table**, which is outside this session's files and is reported rather than
edited.

Naming the wrong company in a privacy policy is the most consequential error
this row could ship, so it is §0 rather than a footnote.

## 1 · THE FINDING THAT MATTERS MOST: `delete` is not `destroy`

There is **no account-deletion endpoint.** `config/routes.rb:267` is
`resources :users, only: %i[index show update]`, and
`app/controllers/api/v1/users_controller.rb:134` holds a **commented-out**
attempt:

```ruby
# def destroy
#   if @user.delete
```

**`User` has 57 associations, nearly all `dependent: :destroy`.** `@user.delete`
skips callbacks and skips every one of those dependents. It would remove the
user row and leave all of it in the database with a dangling `user_id`: **the
endpoint returns 200, the person believes they are gone, and their loans and
contacts are still there — orphaned, unowned and unreachable.**

So the endpoint must use **`destroy`**, and that one word is the whole
difference between his instruction and its opposite. **It is a good thing this
was never finished.**

**One honest exception**, verified at `app/models/user.rb:77`:
`has_many :ai_usage_events, dependent: :nullify` — kept deliberately, because
what the assistant cost is a billing record rather than personal content. **That
exception belongs in the policy text, not hidden in a model file.** "Everything"
with a stated exception is honest; "everything" with an unstated one is not.

## 3 · The disagreements, and how we resolved them

### 3.1 · The row is alone on its own screen — Character AI's shape, taken furthest

Crouton separates by card, Glassdoor by divider, Character AI by whole screen.
**We take the screen**, and for a reason none of them has: **this app already
has a delete two rows away that is SAFE BY CONSTRUCTION.** Deleting a
conversation cannot touch a note, a loan or a contact — the guarantee is by
scoping and `BRIEF.md` §2a is the verification. Deleting the account removes his
life's records.

**They must not look like siblings.** So they differ in every dimension we have:

| | delete a conversation | delete the account |
|---|---|---|
| **where** | a row in the sessions sheet | its own screen, under `Account` |
| **shape** | overflow → confirm dialog | a row → **a full screen** |
| **what the confirm says** | what is **safe** — "your notes, contacts, loans and money are not touched" | what **goes**, named in a list |
| **guard** | a button | **the password, typed again** |
| **colour** | `danger` on one word | `danger` on the row, the heading and the action |

The sessions-sheet delete's confirm names what is safe because that is the
guarantee he asked for. This one cannot: nothing is safe. Naming what goes is
the same discipline pointed the other way.

### 3.2 · The password, typed again — further than all eleven

FotMob is the only reference that re-authenticates, and it does it by sending
you to a login screen. Nothing types a password inline.

**We do, and the argument is what is behind the account rather than what other
apps do:** none of the eleven deletes a corpus of somebody's notes, loans,
contacts and calendar — they delete a watch history, a recipe list, a fan
profile. And this account is reachable from a phone somebody else might be
holding. A checkbox is not a guard against the person holding an unlocked phone;
a password is.

### 3.3 · No table of contents — three references have one and ours does not need it

Flo, Skillshare and HBX all open with a contents list, and all three are
legal-register policies of 13+ sections. **Ours is nine sections of plain
English**, each a few lines. A contents page for that is a screen to scroll past
before reaching a document that is shorter than the contents implied.

### 3.4 · Rendered in the app, never a web view

Peloton's opens `onepeloton.com` in a browser. Ours renders the bundled text, so
it works **on a bad connection** — the condition this whole app is designed for
(`BRIEF.md` §1) — and does not look like leaving the app. It is also the only
version that cannot show a 404 to a store reviewer.

## 4 · Our decisions

- **The source of truth is `docs/PRIVACY.draft.md`, and it is rendered, not
  copied.** `src/content/privacy.generated.ts` is produced from it by
  `scripts/build-privacy.mjs`, and `src/content/__tests__/privacy.test.ts`
  fails if the two drift. A policy that can go stale against its own source is
  worse than one that is hard to edit.
- **The `Notes for Hamma9900` section is STRIPPED at render time and STAYS IN
  THE FILE.** It is the record of two false sentences the multi_magic session
  caught — the DeepSeek/Google one and the "random, not derived from your
  hardware" one — and that record belongs in the repo. Deleting it to make the
  render simple would delete the evidence that the page is checked.
- **While it is a draft, the screen says so.** The file's own first line is
  *"DRAFT, needs Hamma9900's approval before it ships"*, so the screen carries a
  banner saying exactly that. **It is a release gate:** the banner disappears
  when the file becomes `PRIVACY.md`, and a store build with the banner still on
  it is a build that went out without his approval.
- **A minimal markdown renderer, not a dependency.** `src/screens/account/Markdown.tsx`
  handles the subset this document uses — `#`/`##`/`###`, `**bold**`,
  paragraphs, `- ` bullets, `---` rules — and `privacy.test.ts` **asserts the
  document stays inside that subset**, so adding a table fails a test rather
  than silently rendering nothing. Same reasoning as `src/api/parse.ts`'s
  header: a dependency is a decision to surface, and this is eighty lines.
- **Deletion is built and HONESTLY GATED.** `ACCOUNT_DELETION_AVAILABLE` is
  `false` in `src/api/account.ts`, with `routes.rb:267` as the citation. The
  confirm screen renders in full — what goes, what is kept and why — and in
  place of the password field it says the action is not available in the app
  yet. **Nobody is walked through typing a password into a wall**, and the
  disclosure a store reviewer needs is on screen either way. When the endpoint
  lands, one constant flips.
- **`DELETE` must be self-only.** The endpoint is `DELETE /api/v1/users/me` or
  `users#destroy` scoped to `current_user` — **never by id**, or the API meant
  for self-service becomes a way to delete somebody else's account.
