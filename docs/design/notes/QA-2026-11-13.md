# Notes — device QA and smoothness pass (2026-11-13)

Android emulator `qa_phone3` (1080×2400, Android 14, Gboard), dev build, Metro in CI mode. Server: the local multi_magic **master**. Everything typed went into invented `[qa-edit]` notes. No real note appears in a screenshot or a fixture.

Scripts:

- `qa/scripts/keyboard_check.py`.
- Flows 27, 27b, 27d, 27f, 27g, 27h (see `qa/FLOW_REGISTER.md`).

## The owner's 7 smoothness checks

| # | Check | Result | Numbers / evidence |
|---|---|---|---|
| 1 | Typing latency, normal note | **PASS** | 468–540 chars in 50-char bursts (`adb input text`): **0 missing, 0 reordered** after the fixes below. Emulator frames: 85–95 % janky, p90 65 ms. The emulator renders in software with two other sessions' jobs on the box, so these frame numbers are not a phone's. |
| 1 | Typing latency, 900 KB note | **NOT EDITABLE (by design now)** | Engine B refuses a document this size: `POSITION_EPOCH_LIMIT_EXCEEDED: position epoch exceeds maxPositionEpochRetainedBytes`. That limit is inside B's compiled Rust core, not configurable from JS. The screen now shows the read view ("cannot open"), and nothing is sent. Opening takes ~16 s from tap to screen. The exact threshold is **NOT MEASURED**: the probe kept losing its way in the app. |
| 2 | Rapid toggles (bold, italic, H1–H3, checklist, bullets, code, on and off) | **PASS** | Flow 27g, rc=0, run back to back with a selection. Server copy before and after: every word kept, and the one typed "Q" lands in the first block, so the caret did not jump. |
| 3 | Undo/redo 30 steps | **PASS** | 30 undos change the text; 30 redos give back the exact text (server copy compared). |
| 4 | Big paste (table + image) | **PASS (our side) / NOT MEASURED (on device)** | A pasted 10×10 table + 300 paragraphs saves as valid web HTML (`editSession.test.ts`). adb cannot put HTML on the emulator clipboard without installing a helper app. Images: engine B's schema has no image node, so a pasted image is dropped (images on mobile are in MISSING_FEATURES). |
| 5 | Bad network | **PASS** | Airplane mode mid-edit → "On this phone only" → back online → **saved exactly once**, with no new keystroke (fixed, see below). Killed mid-edit while offline: the draft is on the phone (`files/note-drafts/9989.json`) and not on the server; reopened → restored and **saved exactly once**. |
| 6 | Round trip phone ↔ web | **PASS** | "[qa-edit] allblocks" (invented): h1–h3, every mark, sub/sup, link, colour, highlight, centred line, nested and numbered-from-3 lists, tasks, quote, Python code, rule, table with a merged cell. All shown in edit mode on the phone (screenshot). Then: phone edit → the production web Tiptap 3.22.5 (oracle, headless) loads it with every node type, **getJSON stable** after reloading its own HTML → web edit → the phone codec reads it with **0 issues** → the phone shows the web's paragraph and edits after it → the oracle again: stable, 0 issues, both edits present. |
| 7 | Lock while typing; rotation with the keyboard up | **PASS** | Lock toggled 4× during a typing burst: app alive, no crash in `logcat -b crash`. Rotated 4× with the keyboard up: alive, no crash. |

Doubled characters (`aa`, `00`, `ff`) are an **adb artifact, not user-facing**.
- `adb input text` gives every key event the same `downTime`. Engine B's duplicate-dispatch guard (`EditorEditTextHardwareInput.kt`) keys on (keyCode, downTime, repeatCount), so it drops the second of two identical keys.
- Evidence, all on the device:
  - title field (plain TextInput) via adb: "AAxx11yy" exact; body via adb: "Ax1y";
  - separate `input keyevent` Z Z Z: "zzz"; "aa11bb" by key events: exact;
  - Maestro `inputText` "x000 off85503 aabbcc": exact;
  - **Gboard key taps** "aabbccoffkeep" (the IME path users take), 120 ms apart: exact.

## Found and fixed on the device (all test-first)

| Finding | Fix | Commit |
|---|---|---|
| The language key never showed after paragraph → code: B's active state lagged behind a whole-document replace | The bar reads "in code" from our copy of the caret's block | 2847ff4 |
| The language search did not take focus, so "pyth" was typed into the note | `autoFocus` on the search | 258572e |
| Sheets with a text field (code language, link, Labels, Edit labels) opened **under** the keyboard | `KeyboardPadding` in each sheet | a23cf67 |
| Back online, nothing was saved until the next keystroke | The saver retries by itself: 2 s, 4 s … 30 s, once, never after dispose | b1807c9 |
| Every keystroke exported and converted the whole note (0.7 s per key on a laptop at 880 KB); characters were lost while typing fast | `onDocumentChange` plus `exportScheduler`: at once when cheap, once per pause when not, and before leaving/lock/archive/structural edits | b1807c9 |
| Opening a long note built the source map (880 KB: 4.7 s instead of 1.2 s on a laptop) | No source map above 256 KB, where the save writes what the web writes; the read view never builds it | b1807c9 |
| After H1→H2→H3 the bar still lit ¶, and ¶ used a stale heading level | A toolbar command flushes the pending conversion and makes the next one urgent | ddb42e9 |
| A 900 KB note was accepted by B and drawn **empty** ("Write something"); typing there could have replaced the note | The screen checks B's copy (not empty, no fewer blocks) and listens to B's errors: any error → read view, nothing more sent | 89595bf, ddb027a |
| After a web edit, the phone reopened the note from the cache of an earlier visit (the saver's version check would have raised a conflict on the first save) | The editor waits for the fetch made on opening; offline, the cached copy + draft open as before | 0bb9068 |
| After a search, the first tap on a result only closed the keyboard | `keyboardShouldPersistTaps="handled"` on the grid | d4cec5e |

## Not measured, and why

- **27e** (reminder + lock against the server): the dev server runs multi_magic master, which drops `launch_time` and `locked`. It needs PRs #22 and #23 (unmerged, by design). Jest and the PRs' request specs cover the logic. To run once they are merged.
- **iOS**: no simulator on this box. The engine B patch covers Swift too (`RenderBridge+Atoms.swift`).
- **The owner's phone checks**: the Pashto keyboard, the Samsung keyboard, iOS dictation, a hardware keyboard on a tablet.
- **The size above which B refuses a note**: somewhere between the small dev notes (editable) and 900 KB (refused).
- **A paste on the device** (see #4).

## Open findings

- **Dark mode, table header row**: the header cells (Item / Plan / Spent) show light text on a near-white fill, so they cannot be read. Seen in the 411 dp dark shots (27c, taken before the latest commits). To fix test-first in the engine theme (header cell fill in `engineTheme`).
